# AutoResearchClaw 安全模型批判性分析

> **为什么写这份文档**:AutoResearchClaw 有一个绕不开的根本性风险——它**执行 LLM 生成的、未经人工审阅的 Python 代码**,还会**按 LLM 或外部数据给出的 URL 去抓取网络资源**。这两件事都是教科书级的攻击面。本文不满足于罗列"系统做了哪些防护",而是做一次**红队视角的批判性评估**:逐层拆解每道防线的**实现机制**,然后追问它**能挡住什么、挡不住什么、为什么、信任边界落在哪里、残留风险有多大**,并结合最近的 SSRF 修复 commit `bc9dd50` 看防护是怎么演进的。文中所有"能绕过/未闭环"的断言都**经过实际运行或读源码核验**,不是空口推测;关键处给出复现命令。
>
> 与 `架构研究.md`(静态结构)、`端到端追踪.md`(数据流)互补,本文专注**安全边界**这一个维度。

---

## 0. 威胁模型:到底在防谁,边界画在哪

评估防护前必须先界定威胁。AutoResearchClaw 的攻击面有三个,按风险从高到低:

**攻击面一:执行 LLM 生成的实验代码(最高危)。** Stage 10 让 LLM 写出几千行 Python,Stage 12 把它在本机或容器里跑起来。这里的关键认知是:**被执行的代码本质上不可信**。它危险不一定是因为"有人攻击",更常见的是三种日常情形——① LLM 对齐失败或单纯写出 bug(比如本想清理临时目录却写成 `shutil.rmtree(home)`);② 上游 prompt/检索内容里被注入了恶意指令,诱导 LLM 生成后门;③ 实验本身要跑的就是不可信的第三方代码/模型。无论哪种,系统都必须假设"这段代码可能做任何事"。

**攻击面二:按 URL 抓取网络资源(SSRF)。** Stage 3/4 文献检索、PDF 抽取、网页爬取都会去访问 URL,而这些 URL 可能来自 LLM 的检索式或外部搜索结果——即不完全受控。经典的服务端请求伪造(SSRF)风险在于:攻击者若能影响目标 URL,就能让**服务器**去访问它本不该访问的内网资源——云厂商的元数据端点 `169.254.169.254`(能偷云凭证)、内部数据库、管理后台等。

**攻击面三:成果与日志外流。** 论文/代码可能被推到 GitHub/HF;日志里可能落下 API key。这一面风险较低,放在治理层一节谈。

下面逐面深入,重点是一和二。

## 1. 第一道防线:执行前的静态 AST 校验(`experiment/validator.py`)

### 1.1 三道检查的串联

生成代码进沙箱前,`validate_code()`(`validator.py:372-404`)按固定顺序跑三道检查,且**语法不过就短路**——因为代码连解析都做不到时,后面的安全扫描和 import 检查都无从谈起:

1. **语法检查** `validate_syntax`(`:314-329`):`ast.parse`,失败立即返回。
2. **安全扫描** `validate_security`(`:332-343`):把代码解析成抽象语法树(AST),交给 `_SecurityVisitor` 遍历比对黑名单。
3. **import 可用性** `validate_imports`(`:346-369`):检查导入的模块是否在"可用集合"里。这里有个**容易被忽略的设计选择**:不在可用集合里的导入只标 **warning(警告)而非 error**(`:362-365`),意味着"用了一个既不在白名单、也不在黑名单的模块"**不会让校验失败**——真正会硬挡的只有 `BANNED_MODULES` 里那十个。

### 1.2 安全扫描依赖的四个名单

安全扫描的全部判断力,来自四个硬编码的名单:

- **`DANGEROUS_CALLS`**(`:67-91`,命中即 **error**):一批**全限定调用名**字符串——`os.system`、`os.popen`、`os.exec*` 全家八个、`os.remove/unlink/rmdir/removedirs`、`subprocess.call/run/Popen/check_call/check_output`、`shutil.rmtree`。注意它匹配的是"`os.system` 这个字面属性链"。
- **`DANGEROUS_BUILTINS`**(`:94-101`,**error**):四个裸内建名——`eval`、`exec`、`compile`、`__import__`。
- **`BANNED_MODULES`**(`:104-117`,**error**):十个整模块禁导入——`subprocess`、`shutil`、`socket`、`http`、`urllib`、`requests`、`ftplib`、`smtplib`、`ctypes`、`signal`。
- **`SAFE_STDLIB`**(`:120-165`)+ **`COMMON_SCIENCE`**(`:167-201`):白名单。这里有两个**对安全分析至关重要的细节**:第一,**`os` 本身在白名单里**——代码里有一句注释直说"os itself is ok, certain calls aren't"(`:145`),意思是只禁 `os` 的特定危险调用,`os` 模块照常可用;第二,**`pickle` 也在白名单里**(`:147`),而 pickle 反序列化是公认的代码执行入口。科学栈白名单很宽,涵盖 torch/tensorflow/jax/transformers/datasets/peft/trl 等。

### 1.3 AST visitor 到底怎么"看"代码

`_SecurityVisitor`(`:209-269`)是个 `ast.NodeVisitor`,**只覆盖两类节点**:

- `visit_Call`(`:217-239`):对每个函数调用,用 `_resolve_call_name` 把被调对象解析成一个名字字符串,再去比对 `DANGEROUS_BUILTINS` 和 `DANGEROUS_CALLS`。
- `visit_Import` / `visit_ImportFrom`(`:243-269`):取导入模块的顶层名,比对 `BANNED_MODULES`。

而 `_resolve_call_name`(`:272-281`)是理解这道防线能力上限的钥匙——它是**纯静态的属性链拼接**:只认 `ast.Name`(裸名字)和 `ast.Attribute`(点号属性),把 `os.system(...)` 这棵 AST 递归拼成字符串 `"os.system"` 来匹配;遇到任何**不是字面属性链**的形式(函数返回值、下标、动态属性)就拼不出来,返回空串,匹配不到。

> **这道防线的本质,一句话:一个基于"字面字符串匹配"的静态 AST 扫描器。** 它的能力完全取决于"危险操作是否以字面形式直接出现在 AST 里"。这个本质决定了它的全部优点和全部盲区。

## 2. AST 扫描的盲区(本报告的批判核心,附实测)

静态 AST 扫描有一个**无法靠"再加几个名单"解决的根本缺陷**:它只看代码的字面结构,看不到运行时的动态行为。任何"在运行时才组装出来"的危险调用,它都看不见。下面逐条说明绕过路径**为什么**有效,并附上我实际跑出来的结果。

**① `getattr` + 字符串拼接,绕过 `DANGEROUS_CALLS`。** 因为 `_resolve_call_name` 只解析字面属性链,而 `getattr(os, "sys"+"tem")("ls")` 的被调对象是一个 `getattr(...)` 调用的返回值,不是 `ast.Attribute`,拼不出 `"os.system"`。实测:

```
validate_code('import os\nos.system("ls")')            → errors: ['Dangerous call: os.system()']   ✅ 挡住
validate_code('import os\ngetattr(os, chr(115)+"ystem")("ls")') → errors: []                        ⚠️ 绕过
```

同理 `globals()["eval"](...)`、`getattr(__builtins__, "ev"+"al")(...)` 也绕过 `DANGEROUS_BUILTINS`——`eval`/`exec` 只要不以裸名字形式出现就抓不到。

**② `importlib` 导入被禁模块,绕过 `BANNED_MODULES`。** `importlib` 不在黑名单里,而且 `importlib.import_module("subprocess")` 是一个**函数调用**,不是 `import` 语句,`visit_Import` 根本不会被触发。实测:

```
validate_code('import importlib\nm=importlib.import_module("subprocess")') → errors: []   ⚠️ 绕过
```

这等于在黑名单(禁了裸 `import subprocess` 和 `__import__`)上开了一扇没锁的后门。

**③ `open()` 任意路径读写,根本不在任何名单里。** `open` 是内建函数,既不在 `DANGEROUS_BUILTINS` 也无从禁(禁了实验代码就没法读写数据了)。而 `os` 只禁了 `remove/unlink/rmdir`,**写文件、覆盖文件完全不管**。实测:

```
validate_code('open("/tmp/x","w").write("x")') → errors: []   ⚠️ 绕过
```

后果:代码可以读宿主机的 `~/.ssh/id_rsa`、`~/.aws/credentials`,或覆盖 `~/.ssh/authorized_keys` 写入攻击者公钥。

**④ 通过白名单科学库联网,绕过网络模块黑名单。** `socket`/`urllib`/`requests` 被禁了,但 `torch`、`datasets`、`transformers` 在白名单里,而这些库内部会发 HTTP 请求(`datasets.load_dataset("...")`、`AutoModel.from_pretrained("...")`、`torch.hub.load(...)` 都会联网下载)。模块级黑名单**管不到白名单库的内部行为**,所以网络外联和数据外泄这条路是通的。

**⑤ `pickle` 反序列化,白名单放行。** `pickle.load(open(untrusted))` 在反序列化时会执行 `__reduce__`,是经典 RCE 入口,但 `pickle` 在 `SAFE_STDLIB` 里。

**⑥ 资源耗尽,AST 不分析运行时开销。** `while True: pass`(吃满 CPU)、`x = [0]*10**12`(吃爆内存)都是合法语法、无危险调用,静态扫描无能为力。这类只能靠执行层的超时/资源限制兜底(见 §4)。

### 小结:这道防线的真实定位

把上面六条放在一起,结论很清楚:**AST 扫描只能拦住"天真地、字面写出来的"危险操作**——`os.system("rm -rf /")`、`import subprocess` 这种。对任何稍有规避意识(哪怕只是用了 `getattr`)的代码,它几乎无效。所以它的**正确定位是"质量粗筛"**:帮 LLM 把明显手滑的危险代码在生成阶段就改掉(配合 §3 的修复循环),而**绝不是对抗恶意代码的安全边界**。真正的边界必须由下一层——操作系统级隔离——来提供。把 AST 扫描当安全闸门,是这个系统最容易产生的误判。

(另一个工程隐患:`validate_code` 有个 `skip_security=True` 开关(`:376`)。应当审计所有调用点,确保生产执行路径上没有人传它。)

## 3. 校验如何接入执行流:它是"门"还是"反馈"?

一个决定性的问题:安全扫描发现 error 后,是**一票否决、拒绝执行**,还是只是**喂给修复循环让 LLM 改**?从代码看,validator 的主要角色是**后者**——`validate_code` 在 Stage 10 代码生成的 `max_repair=5` 循环里被反复调用,`format_issues_for_llm`(`:412-422`)把问题列表格式化后回灌给 LLM,让它在下一轮把代码改干净(机制详见 `架构研究.md §8.2`)。

这进一步印证了 §2 的结论:**不能把 AST 扫描理解成"执行前的安全闸门",它是质量反馈回路的一环**。一段恶意代码若从一开始就用 `getattr` 规避,扫描根本不会报错,修复循环也就不会被触发,代码会原样进入执行层。所以"危险代码到底会不会伤到宿主机",最终**不取决于 validator,而取决于它在什么环境里被执行**。

## 4. 第二道防线:沙箱隔离分层(真正的安全边界所在)

`config.experiment.mode` 决定代码在哪种环境执行,而**不同模式的隔离强度天差地别**——这是整个安全模型里最该被认清、也最容易被忽视的一点(模式总览见 `架构研究.md §11`)。

### 4.1 各模式的隔离强度与批判

**`simulated`**:不真正执行代码(返回 mock 结果)。绝对安全,但也没做真实验。

**`sandbox`(本机子进程)——几乎没有 OS 级隔离 ⚠️。** 这是最该警惕的配置。它通过 `subprocess` 在**本机、以当前用户的权限**直接跑生成代码,拥有完整的文件系统访问和网络访问。它唯一的防护就是 §1 那个**能被绕过的 AST 扫描**,外加两道轻量措施(下文 4.2)。换句话说:**在 sandbox 模式下,一段刻意规避或被注入的 LLM 代码,可以读取宿主机的任何文件、写任意位置、对外联网**,因为根本没有一个 OS 边界把它关起来。如果这是默认/常用模式,使用者必须清楚自己是在"用宿主机权限运行不可信代码"。

**`docker`(容器隔离 + 网络策略)——这才是真正的边界 ✅,但有细节弱点。** Docker 模式把代码关进容器,并提供 `network_policy` 三档(`docker_sandbox.py:403-417`):
- `none`:全程 `--network none`,容器没有任何网络——最安全;
- `setup_only`/`pip_only`:Phase 0/1(pip 安装、数据下载)允许联网,进入 Phase 2(跑实验)前用 iptables 切断。**但这里有个真实弱点**(`:408-413` 注释明说):iptables 需要 `NET_ADMIN` 能力/root,**如果运行用户没有该权限,会"优雅降级"——网络反而保持开启**,只是代码可能因预期断网而出错。也就是说,`setup_only` 的断网保证**不是强保证**,在非 root 环境下可能形同虚设;
- `full`:全程联网,仅供调试。

容器本身也并非铁板一块:从启动命令看,设了 `--memory` 内存上限(`:389`),但**没看到 `--pids-limit`(防 fork 炸弹)、`--read-only`、`cap-drop=ALL` 等收紧措施**,而 GPU 模式会 `--gpus all`(`:225`)做设备透传——GPU 透传本身会扩大攻击面。容器逃逸、内核漏洞等风险依然存在,但比 sandbox 模式强了一个数量级。

**`ssh_remote`**:把执行风险**转移**到远程机——远程机若是一次性/隔离的还好,否则只是换个地方裸跑。**`colab_drive`**:Colab 一次性环境,隔离较好。

### 4.2 沙箱执行前的两道轻量措施(`sandbox.py:385-451`)

无论哪种模式,沙箱在跑代码前还做两件事:
- **注入不可变的 `experiment_harness.py`**:一个固定的度量/打印框架,防止生成代码篡改度量逻辑、伪造结果。(注意 `experiment_harness` 也在 `COMMON_SCIENCE` 白名单里,所以生成代码可以正常 import 它。)
- **符号链接逃逸检查** `validate_entry_point_resolved`(`:40-50`):把工程复制到 staging 目录后,检查入口点 `resolve()` 之后仍落在 staging 内,挡住 `../../etc/passwd` 这类用符号链接/相对路径逃出工作目录的把戏。

这两道措施是有意义的,但都是**针对特定小手法的点防御**,不改变"sandbox 模式无 OS 隔离"的大局。

> **本节核心批判**:安全强度**高度依赖运行模式**。`docker(network=none)` 及以上才提供真正的边界;`sandbox` 本机模式下,唯一防线是可绕过的静态扫描,实质等于裸跑不可信代码。而即便选了 docker 的 `setup_only`,断网还依赖 root 权限,非 root 下可能不生效。**建议:对不可信来源的 topic,默认强制 `docker` + `network_policy=none`,并确认运行环境具备 NET_ADMIN。**

## 5. 第三个攻击面:SSRF 与 `check_url_ssrf`(`web/_ssrf.py`)

文献检索(`search.py`)、PDF 抽取(`pdf_extractor.py`)、网页爬取(`crawler.py`)都会按 URL 发起请求,统一先过 `check_url_ssrf(url)` 这道关。这个函数全文仅约 50 行,逻辑清晰:

```python
if "\\" in url: return "...backslash..."                                  # bc9dd50 新增
if "@" in url.split("//",1)[-1].split("/",1)[0]: return "...userinfo..."  # bc9dd50 新增
parsed = urlparse(url)
if parsed.scheme not in ("http","https"): return "Unsupported scheme"      # 挡 file://、gopher:// 等
hostname = parsed.hostname or ""
# 字面 IP 直接 parse;域名走 getaddrinfo 解析成 IP
if addr.is_private or addr.is_loopback or addr.is_link_local or addr.is_reserved:
    return "Blocked internal/private URL"                                  # 挡私网/环回/链路本地/保留
return None
```

它**确实挡住了**:非 http(s) 协议、RFC1918 私网、环回 `127.0.0.1`、链路本地(含云元数据端点 `169.254.169.254`,属 link-local)、保留地址。我实测确认:

```
check_url_ssrf('http://169.254.169.254/latest/meta-data/') → Blocked internal/private URL   ✅
check_url_ssrf('http://trusted.com@127.0.0.1/')            → Blocked ...userinfo...          ✅
check_url_ssrf('http://a\\b/')                              → Blocked ...backslash...          ✅
```

### 5.1 commit `bc9dd50` 修的是哪类绕过

这个 commit(issue #254)堵的是**URL 解析歧义**类绕过——这类绕过的本质是"不同组件对同一个 URL 解析出不同的 host":
- **反斜杠**:某些解析器对 `\` 的处理与 `urlparse`/浏览器不一致,攻击者可构造 `http://expected.com\@evil-internal/`,让校验组件和实际请求组件看到不同的 host。修复直接**拒绝任何含 `\` 的 URL**。
- **userinfo**:`http://trusted.com@169.254.169.254/` 里,`@` 之前是 userinfo(用户名),真正的 host 是 `@` 之后的内网地址;天真的字符串判断会误以为 host 是 `trusted.com`。修复**拒绝 host 段含 `@` 的 URL**。

这是**正确且必要**的加固,精准打击了一类经典 SSRF 绕过。

### 5.2 残留风险(经读源码核验,不是推测)

但 SSRF 防护**远未闭环**。我读了真正发请求的 `crawler.py`,确认了两个最经典的 SSRF 绕过仍然成立:

**① DNS rebinding / TOCTOU(检查与使用的时间差)。** `check_url_ssrf` 用 `getaddrinfo` 解析**一次**做判断(`_ssrf.py:39`),但真正发请求时——`crawler._crawl_with_urllib` 里的 `urlopen(req)`(`crawler.py:211`)——**会再解析一次 DNS**。这两次解析之间有时间差,攻击者控制的 DNS 可以让第一次返回公网 IP(通过校验)、第二次返回 `127.0.0.1`(实际访问内网)。校验拿到的 IP 没有被"锁定"后传给请求层复用,洞就存在。

**② HTTP 重定向跟随,且每一跳不重新校验。** `check_url_ssrf` 只在**原始 URL** 上查一次(`crawler.py:74` 进入时查),之后的 `urlopen`(`:211`)是**默认配置、没有自定义 redirect handler**,而 urllib 默认会跟随 30x 重定向。于是攻击者给一个通过校验的公网 URL,服务器 301 重定向到 `http://169.254.169.254/`,`urlopen` 就乖乖跟过去了——**中间没有任何一跳重新过 `check_url_ssrf`**。crawl4ai 的无头浏览器路径(`:117-143`)同样会跟随重定向并重新解析 DNS,问题一样。

**③ 地址变体。** IPv4-mapped IPv6(`::ffff:127.0.0.1`)、十进制/八进制 IP(`http://2130706433/`)等变体是否都被 `ipaddress` 的 `is_*` 系列覆盖,需逐一确认;`ipaddress` 覆盖了一部分但不保证全部。

**④ 解析失败即放行。** `getaddrinfo` 失败时函数返回 `None`(放行,注释说"让请求自然失败",`:38-40`)。这是可接受的权衡,但意味着 DNS 层的怪异输入不在这里拦。

> **SSRF 评估**:`bc9dd50` 修的解析歧义洞是真问题、修得对、实测有效;但**DNS rebinding 和重定向跟随这两个最经典的 SSRF 绕过尚未闭环**——已通过阅读 `crawler.py`(单次校验 + 默认 urlopen 跟重定向 + 二次 DNS 解析)确认。这是 SSRF 这条线最该优先复查的地方。

## 6. 同一 commit 的另一半:域探测器子串误判(鲁棒性,非安全)

`bc9dd50` 还修了 `domains/detector.py` 一个**鲁棒性**(非安全)bug(issue #261):关键词匹配原本用裸 `in` 子串匹配,导致短词误命中——例如 "dataset" 含子串 "set",让普通 ML 主题被误判成 `physics_simulation`。修复改为:**长度 <5 的短关键词改用词边界正则 `\b...\b` 匹配**,长词仍用子串(`detector.py:_keyword_detect`)。这虽不属安全问题,但和 SSRF 修复同属"**修正天真字符串匹配带来的歧义**"这一类思路,放在一个 commit 里有内在一致性,值得一并记录。

## 7. 治理层控制(流程性安全)

除技术隔离外,还有几个流程层面的纵深控制(详见 `架构研究.md §2/§10/§12`):

- **发布闸门**:`security.allow_publish_without_approval` 默认 `False`(`config.py:951-959`),即把论文/代码导出到 GitHub/HF 默认需要人工审批;Stage 20 是质检闸门。这把"成果外流"挡在人工确认之后,降低了"自动把含敏感信息的产物推到公网"的风险。
- **`hitl_required_stages` 默认 `(5,9,20)`**:在文献筛选、**实验设计**、质检三处强制人介入。其中实验设计(Stage 9)的人审,理论上是拦截"危险实验方案"的一个机会窗口——但前提是审的人真的会逐条看方案,这在自动化压力下未必成立。
- **`redact_sensitive_logs` 默认 `True`**:日志写盘前抹掉 API key 等敏感串,降低日志泄密面。

这些控制是有价值的纵深,但共同依赖两个脆弱前提:**人真的会认真审**,以及**配置没有被为了"省事"而关掉**。

## 8. 信任边界总图与残留风险评级

```
┌─────────────────────────────────────────────────────────────────┐
│  不可信输入:LLM 生成的代码 / LLM 或外部数据给出的 URL              │
└─────────────────────────────────────────────────────────────────┘
        │ 代码                                  │ URL
        ▼                                       ▼
  [L1 静态 AST 扫描]                         [check_url_ssrf]
   实测可被 getattr/importlib/open 绕过        修了解析歧义(✅)
   → 定位:质量粗筛,非安全边界                 但 DNS rebinding/重定向未闭环(实测确认)
        │                                       │
        ▼                                       ▼
  [L2 沙箱执行] ← 真正的边界在这里            [urlopen 实际请求]
   ├ sandbox = 本机子进程,几乎无隔离 ⚠️         默认跟随重定向 + 二次 DNS 解析
   ├ docker(none) = 真边界 ✅                  → 上述绕过得以实现
   ├ docker(setup_only) = 断网依赖 root,
   │   非 root 下降级为不断网 ⚠️
   └ ssh/colab = 异地/一次性隔离
        │
        ▼
  [L3 治理:HITL 发布闸门 / 实验设计人审 / 日志脱敏] ← 依赖"人真审"+"配置没关"
```

**残留风险评级**:

| 风险 | 等级 | 依据 |
|------|------|------|
| `sandbox` 模式下执行规避型/被注入的恶意代码 | **高** | AST 扫描实测可绕过;本机子进程无 OS 隔离 |
| 通过白名单库(torch/datasets/transformers)网络外泄 | **中-高** | 模块黑名单管不到库内部 HTTP |
| `open()` 任意文件读写 / `pickle` 反序列化 | **中-高** | 实测不在任何黑名单 |
| SSRF via DNS rebinding / 重定向跟随 | **中** | 读 crawler.py 确认:单次校验 + urlopen 跟重定向 + 二次解析 |
| docker `setup_only` 非 root 环境断网失效 | **中** | docker_sandbox.py:410-413 注释明示优雅降级 |
| 资源耗尽(CPU/内存/死循环/fork) | **中** | 仅 time_budget 超时兜底;未见 pids-limit |
| 成果未经审批外流 | **低** | 默认需人审批 + 质检闸门 |
| 日志泄密 | **低** | 默认脱敏 |

## 9. 改进建议(按性价比排序)

1. **默认即隔离(最高优先级)**:对不可信/外部来源的 topic,默认强制 `docker` + `network_policy=none`,并校验运行环境具备 `NET_ADMIN`(否则 `setup_only` 的断网是假的)。这一条用 L2 的真边界,兜住 L1 的固有缺陷,是性价比最高的加固。
2. **SSRF 闭环**:在 fetch 层做两件事——(a)校验时解析出的 IP **锁定并直连**,杜绝 DNS rebinding;(b)对**每一跳重定向**重新跑 `check_url_ssrf`(给 urllib 装一个拒绝/校验重定向的 handler,或显式 `allow_redirects=False` 后手动逐跳校验)。
3. **容器收紧**:docker 启动加 `--pids-limit`(防 fork 炸弹)、`--read-only` + 显式可写卷、`--cap-drop=ALL` 再按需 add,GPU 透传仅在确需时开。
4. **补 AST 名单的明显遗漏 + 审计开关**:把 `importlib`、`pickle`(或限制)、可疑 `getattr`/`open(...,'w')` 纳入扫描或告警;审计所有 `skip_security=True` 调用点。但要清醒——**这只是抬高绕过门槛,静态扫描永远不是边界**。
5. **资源硬限制**:在容器层用 cgroup 限制 CPU/内存/进程数,而不只靠 wall-clock 超时。

> **总结**:AutoResearchClaw 的安全**架构思路是对的**——粗筛(L1)+ 隔离(L2)+ 人审(L3)三层纵深,最近的 SSRF 修复也精准。但**实际安全强度高度依赖运行配置**:只有 `docker(network=none)` 及以上才是真边界;`sandbox` 本机模式下静态扫描可被绕过,几乎等于裸跑不可信代码;即便 docker 的 `setup_only`,断网还依赖 root。把"默认强隔离"和"SSRF 的 DNS-rebinding/重定向闭环"补上,是当前性价比最高的两项加固。
