# Stage 10 → 12 冒烟测试(Smoke Test)

> 引入提交:`d025162`(harness + config + prompt)、`e435297`(配套可观测)。
> 定位:**流水线设计层缺陷的修复** —— 代码生成(Stage 10)与全量执行(Stage 12)之间原本没有任何运行时验证关。

---

## 1. 针对什么 bug

第四轮(run-4)反复被 beast 生成的**随机运行时逻辑 bug**卡住:每次重跑 Stage 10,生成的 `main.py` 都语法合法、能通过 validator 的 AST/import 静态检查,却在 Stage 12 全量执行时崩溃。已撞到的实例:

| # | bug | 崩溃点 | 现象 |
|---|-----|--------|------|
| 1 | 双重转换 `deepcad_json_to_cadquery(extract_text_from_sample(...))` | 数据准备 | GT 校准=0,全条件 0 |
| 2 | `from deepcad_transpiler import get_operation_count`(名不存在) | 启动 import | ImportError 即崩 |
| 3 | `prepare_sft_texts` 里 `dataset_split=None` 覆盖入参 | 数据准备 | `len(None)` 崩每个条件 |
| 4 | `device_map={'':0}` 但未限 `CUDA_VISIBLE_DEVICES` → HF Trainer 自动 DataParallel | `trainer.train()` first step | `chunk expects ≥1-dim tensor` |

**共同特征**:① validator 抓不到(都是运行时逻辑/配置错,非语法/import-name 静态可见);② **全部在启动 / 数据准备 / first-step 的头几分钟内崩**,没有一个崩在深度训练之后。

**根本痛点**:这类是随机噪声,逐个写 prompt 规则=打地鼠;真正缺的是**生成后、全量前的一道运行时验证关**。每次"全量跑几小时才发现崩"代价极高(run-4 因此耗了数天)。

---

## 2. 采取的办法

**在 Stage 10 代码生成 + 校验之后、Stage 12 全量执行之前,加一道冒烟测试**:用极小预算把生成的项目真跑一遍,几分钟内抓出上述运行时崩溃,把 traceback 喂回修复循环,修不好就阻断 stage。

利用了"目标 bug 都在头几分钟内崩"这一特征:**即便生成代码不缩小规模,带紧超时跑一段不崩 = 启动类 bug 已排除**。配合 `ARC_SMOKE` 钩子则能在 1–2 分钟内完整跑完所有条件。

### 三态判定
`_run_smoke_test()` 用 `ARC_SMOKE=1` + 限时跑 `main.py`,返回:
- **pass**:① 干净退出(returncode 0);**或** ② 跑满超时窗口未崩(启动类 bug 已排除,视为通过)。
- **fail**:进程非零退出 → 取 `stderr` 末尾(traceback)交给修复循环。
- **skip**:冒烟框架自身报错(如沙箱创建失败)→ 不阻断 stage(只告警)。

### 修复循环(复用 rigor-repair 模式)
fail → 把 traceback 喂回 LLM(要求修根因)→ `_extract_multi_file_blocks(assume_main=False)` 提取 + **merge** 进 files + 重写 `experiment/` → 重跑冒烟。最多 **2 次**。仍 fail → 写 `SMOKE_FAILED.md` 并返回 `StageResult(FAILED)`,阻断进入 Stage 12。

## 3. 对原项目的改动

### 3.1 配置 `researchclaw/config.py`
`ExperimentConfig` 新增两字段(及 YAML loader 解析):

| 字段 | 默认 | 含义 |
|------|------|------|
| `smoke_test_enabled` | `True` | 是否启用冒烟测试 |
| `smoke_test_timeout_sec` | `600` | `main.py` 执行的限时(秒;**不含** provisioning,后者用 `provision_timeout_sec`) |

YAML 覆盖示例(`config.arc.yaml` 的 `experiment:` 段下):
```yaml
experiment:
  smoke_test_enabled: true        # 关掉冒烟:false
  smoke_test_timeout_sec: 600
```

### 3.2 harness `researchclaw/pipeline/stage_impls/_code_generation.py`
- 新增 `_run_smoke_test(exp_dir, config, timeout_sec) -> (status, detail)`(三态)。
- 在 Stage 10 最终 `return` 前插入:**门控** + 冒烟 + 修复循环 + `SMOKE_FAILED.md` 阻断。
- **门控条件**(全满足才跑冒烟):
  `smoke_test_enabled` 且 `mode ∈ {sandbox, docker}` 且 `files` 含 `main.py` 且**对应 mode 的 `network_policy != "none"`**(docker 读 `docker.network_policy`、sandbox 读 `sandbox.network_policy`;必须能 provisioning,否则缺依赖会误报)。

### 3.3 codegen prompt `opencode_bridge.py`(beast)+ `prompts/ml.py`(ml)
新增 **`ARC_SMOKE` 钩子**约定:要求 `main()` 顶部 `if os.environ.get("ARC_SMOKE")` 时把**每个成本旋钮缩到最小但仍覆盖每条件路径**(seeds=[0]、train steps/epochs→1、eval/proxy/collection 样本→2、RL steps→1、数据集→几行),使冒烟在 1–2 分钟跑完**所有**条件、并仍触达真实工具/oracle(只缩规模,不换实现)。

### 3.4 配套可观测(`e435297`,使冒烟失败时能定位)
- codegen prompt 要求:**每个长循环**(训练/eval/proxy/rollout)定期更新 `progress.json` 并打印进度;
- **except 必须 `traceback.print_exc()`**(注意 sandbox 把 stderr 单独落 `stderr.log`)——否则冒烟 fail 只有一行消息、定位不到根因。

### 3.5 产物
- 失败时:`stage-10/SMOKE_FAILED.md`(含 traceback,gate 可见),stage 状态 `FAILED`。
- 冒烟自身的沙箱:`stage-10/smoke_sandbox/_project_N/`(独立 venv + stdout.log/stderr.log)。

## 4. 运行中要注意什么

1. **首次 provisioning 开销**:冒烟会在 `smoke_sandbox` 建独立 venv + pip(~10 min,一次性)。Stage 12 之后还会再建一次自己的 venv(**目前不复用**,合计多 ~10 min)。相对全量几十小时、以及"全量跑崩重来"的代价,可忽略。**待优化**:让 Stage 12 复用冒烟的 venv。
2. **依赖必须可装**:门控要求 `network_policy != none`。若设 `none`(不 provisioning),冒烟会因缺依赖**误报 fail**——这是故意不在该模式下跑冒烟的原因。
3. **`ARC_SMOKE` 是 prompt 约定,靠 LLM 遵守**:若新生成的 `main.py` 没实现该钩子,冒烟会跑**全量规模**→大概率在 `smoke_test_timeout_sec`(600s)超时 → 判 **pass(inconclusive)**。这仍能抓住"头几分钟崩"的目标 bug,但**不能确认**深层路径。**发车后应验收**新 `main.py` 是否真有 `ARC_SMOKE` 分支(grep `ARC_SMOKE`)。
4. **超时语义**:600s 是 `main.py` 执行限时,**不含 provisioning**。若某条件单步极慢(如未提速的 eval),即便 ARC_SMOKE 缩到 2 样本也可能逼近 600s——观察到频繁超时-pass 时,考虑调大 `smoke_test_timeout_sec` 或确认提速(fp16/批量/紧cap)已生效。
5. **修复循环上限 2 次**:连续两次 traceback 修不好就阻断。看到 `SMOKE_FAILED.md` 说明是 LLM 难自修的 bug,需人工看 traceback。
6. **stderr vs stdout**:冒烟的 traceback 在 `smoke_sandbox/_project_N/stderr.log`;`SMOKE_FAILED.md` 已摘录末尾。巡检/排查直接看这两处。
7. **skip 不阻断**:若日志出现 "smoke test harness error",是冒烟框架自身问题(非生成代码 bug),stage 照常放行——需留意不要把真问题误当 skip 放过。
