# AutoResearchClaw 端到端追踪:一个 hypothesis 如何从 Stage 8 走到 Stage 12

> **为什么写这份文档**:`架构研究.md` 描述了系统的静态结构——状态机怎么转、闸门怎么守、各子系统各司什么职。但一条科研流水线真正的"魔法"在于**信息形态的逐跳坍缩**:一句用自然语言写成的科学假设,如何一步步变成结构化的实验方案、变成几千行可运行的 Python、变成一张任务依赖图,最终变成一个可以反过来检验这句假设的数字字典。本文选定**一条真实假设**作为贯穿样本(取自 artifact `rc-20260425-054156-fdedd0`,主题"为参数化 CAD 建模微调 LLM"),沿 Stage 8 → 12 的五跳逐段拆解:每一跳**读入什么、内部怎么加工、写出什么、数据形态如何改变、为什么这样设计、出错时怎么兜底**。所有结论均有 `file:line` 证据并经实际代码核验。
>
> 本文是 `架构研究.md` 的动态补充:那篇讲"机器由哪些零件构成",这篇讲"一份数据如何穿过这些零件"。涉及"怎么生成代码""怎么分析结果"等纵深机制时,本文会指向 `架构研究.md` 对应小节,避免重复。

## 0. 追踪对象、全景与贯穿原理

### 0.1 被追踪的假设

```
H1:为 CAD 操作建立"原语级"专用 token(每个草图/拉伸操作一个 token),
    相比标准 BPE 子词切分,能让生成的 CAD 序列几何有效率(validity rate)
    提升 ≥20 个百分点。
```

这句话的特点是它**自带可测预测(≥20pp)和证伪条件**——这正是后续每一跳能把它"翻译"成实验参数的前提。本文会跟着它走完整条流水线,看它如何在每一跳被具体化。

### 0.2 五跳全景

```
Stage 8  hypotheses.md
   │  (半结构化 markdown:假设 + 可测预测 + 证伪条件 + 资源估算)
   ▼
Stage 9  exp_plan.yaml  (+ domain_profile.json)
   │  (结构化方案:baselines / proposed_methods / ablations / metrics / compute_budget)
   ├──────────────┬──────────────────────────────
   ▼              ▼
Stage 10        Stage 11
experiment/     schedule.json
(main.py +      (22 任务的依赖 DAG)
 6 个模块)            │
   │                 │
   └────────┬────────┘
            ▼
        Stage 12  runs/run-1.json + results.json
            │  (机器可读的分层 metrics 字典)
            ▼
        Stage 13 / 14  读 runs/ → 检验 H1 → 决策 proceed/refine/pivot
```

### 0.3 贯穿全程的衔接原理:文件名契约

整条流水线的相邻阶段不是通过内存对象传参连接的,而是通过**写到磁盘的文件 + 一份声明了"我需要哪些文件、我会产出哪些文件"的契约**(`pipeline/contracts.py` 里每个阶段的 `StageContract`)来焊接。下表是本文涉及的五个阶段的契约,已用真实代码核验完全一致:

| 阶段 | input_files(读) | output_files(写) | Definition of Done |
|------|------------------|--------------------|--------------------|
| 8 HYPOTHESIS_GEN | `synthesis.md` | `hypotheses.md` | ≥2 个可证伪假设 |
| 9 EXPERIMENT_DESIGN | `hypotheses.md` | `exp_plan.yaml` | 含 baseline/消融/指标的方案并通过审批 |
| 10 CODE_GENERATION | `exp_plan.yaml` | `experiment/`, `experiment_spec.md` | 多文件实验工程 + 规格文档 |
| 11 RESOURCE_PLANNING | `exp_plan.yaml` | `schedule.json` | 带 GPU/时间估算的资源排程 |
| 12 EXPERIMENT_RUN | `schedule.json`, `experiment/` | `runs/` | 全部排程跑完并留下产物 |

这个设计不是偶然的。**用纯文件名而非内存对象衔接,直接换来了四个能力**:① 任何阶段都能用 `--from-stage` 单独重跑,因为它的输入就是磁盘上现成的文件;② 进程崩溃后能从 checkpoint 续跑(下一阶段照样从磁盘读上一阶段产物);③ HITL(人机协作)可以在两个阶段之间**手动编辑中间产物**(比如人改一下 `exp_plan.yaml` 再继续);④ 执行器可以在调用阶段逻辑前后做机械的契约校验——执行前检查 `input_files` 是否都在(`executor.py:615-627`),执行后检查 `output_files` 是否存在且非空(`executor.py:681-705`),任一不满足就立刻判失败,把错误挡在源头而不让它级联到下游。

## 1. 第①跳 Stage 8 → 9:从一句话假设到一份 YAML 方案

这一跳完成的是整条流水线里语义跨度最大的转换之一:**自然语言 → 结构化实验设计**。

### 1.1 Stage 8 写出的 `hypotheses.md` 长什么样

Stage 8(`stage_impls/_synthesis.py:92-198`)的产物 `hypotheses.md` 是一份**半结构化 markdown**——它有稳定的语义骨架,但不是严格的机器 schema(这是有意为之:假设是要给人读、也要给下一个 LLM 读的,markdown 比 JSON 更适合承载论证)。`_default_hypotheses()`(`:1580-1594`)给出了兜底骨架,真实产物里每条假设包含这几块:

- `### Hypothesis N: <标题>` —— 假设本身,一句可证伪的断言;
- `**Rationale**` —— 科学依据,解释为什么值得验证;
- `**Measurable Prediction**` —— **可量化预测**,这是后续翻译成指标的关键。本例 H1 这里写的就是"≥20 个百分点的有效率提升",还可能带诊断性子断言(用来区分"是真推理还是检索")和 scaling probe(在不同模型规模上重复);
- `**Failure Condition**` —— 证伪条件,即什么情况下这条假设被推翻;
- `**Resource Requirement**` —— 算力/时间/工程量预算估计。

文件末尾还有两个全局段落:`## Unresolved Disagreements`(保留 Stage 8 多角色辩论里没达成一致的分歧点)和 `## Recommended Sequencing`(决策门建议:比如"若 H1 成立再做 H2,否则转 H3")。

除了主产物,Stage 8 还写两份副产物:`perspectives/<role>.md`(辩论里每个角色——ML 域的 innovator/pragmatist/contrarian——各自的原始输出,`_helpers.py:711`),以及 `novelty_report.json`(对照已采集文献给出的 `{novelty_score, assessment, recommendation}`,**非阻断**:外部 API 失败只记日志不影响本阶段,`:179`)。

### 1.2 Stage 9 如何读入假设,以及一个容易忽略的截断

Stage 9(`_experiment_design.py:74-86`)一进门就读假设:

```python
hypotheses = _read_prior_artifact(run_dir, "hypotheses.md") or ""   # :83
preamble = _build_context_preamble(config, run_dir,
              include_goal=True, include_hypotheses=True)            # :85
```

这里有个**关键且容易被忽略的细节**:假设在两个地方进入 prompt,处理方式不同。`_build_context_preamble` 构造的"上下文前言"里,假设被截断到 `hyp[:2200]` 字符(`_helpers.py:1061`);而完整的假设文本另由 `{hypotheses}` 占位符单独注入。为什么要这样分?因为前言是用来给 LLM 提供"背景概览"的,如果把整篇长假设塞进去,会挤占本就有限的输出 token 预算(实验方案 YAML 本身就很长);所以前言里放截断版做概览,完整版单独给一次。这是一个在 prompt 工程里很典型的"概览 vs 全文"权衡。

### 1.3 Prompt 远不止"假设 + 要求"——十几个上下文变量的注入

之前的版本把这一步简化成"注入假设,要求输出 YAML",但真实的 prompt 组装(`:200-214`)注入了**十多个上下文变量**,每个都在塑造 LLM 的输出:

```python
sp = _pm.for_stage("experiment_design",
        evolution_overlay=_overlay,          # 跨轮经验(若有 pivot 历史)
        preamble=preamble,                   # 含截断假设的背景前言
        hypotheses=hypotheses,               # 完整假设全文
        dataset_guidance=_dg_block,          # 数据集指引(RL 主题还会追加 RL 步数指引)
        domain_design_context=_domain_design_context,  # 非 ML 域的 YAML 注入指引
        time_budget_sec=config.experiment.time_budget_sec,
        metric_key=config.experiment.metric_key,
        metric_direction=config.experiment.metric_direction,
        hardware_profile=_hw_profile_str,    # GPU 型号/显存
        per_condition_budget_sec=_per_condition_sec,  # = time_budget*0.7/6
        available_tier1_datasets=_tier1)
```

几个值得注意的动态行为:
- **RL 主题特判**(`:156-180`):如果 topic 含 "reinforcement learning"/"ppo"/"mujoco" 等关键词,会追加 RL 步数指引;若时间预算 ≤3600s 还会**强制**只用经典控制环境(CartPole/Pendulum 等),≤1800s 则进一步收窄到最简单的两个——因为 MuJoCo 这类环境没有 5000s 以上根本训不出有意义结果。这是把"算力现实"硬编码进 prompt,防止 LLM 设计出注定超时的实验。
- **框架文档注入**(`:181-190`):`detect_frameworks` 从 topic/假设里探测涉及的框架,`load_framework_docs` 拉最多 4000 字符的文档片段进 prompt,让生成的方案贴合真实 API。
- **领域探测先行**(下一小节)。

prompt 模板(`prompts.default.yaml:94-105`)最后硬性要求:输出 YAML,且必须含 `objectives, datasets, baselines, proposed_methods, ablations, metrics, risks, compute_budget` 八个键。

### 1.4 领域探测:决定后续用什么"科研范式"

在调 LLM 之前,Stage 9 先做领域探测(`:89-118`):

```python
_domain_profile = detect_domain(topic=config.research.topic, hypotheses=hypotheses)
```

它根据 topic 和假设文本判定研究属于哪个领域,并落盘 `domain_profile.json`:`{domain_id, display_name, experiment_paradigm, core_libraries, gpu_required}`。这份 profile 不只是元数据——`experiment_paradigm`(comparison / convergence / simulation / ablation_study)会影响实验该怎么组织,`core_libraries` 会传给 Stage 10 选库,`gpu_required` 影响资源规划。对 ML/HEP 这种已有原生 prompt bank 的域,行为不变;对 biology/physics/economics 等域,会通过 `GenericPromptAdapter` 把 YAML 定义的领域指引注入到 `_domain_design_context` 里(`:124-147`)。

### 1.5 Stage 9 写出的 `exp_plan.yaml`:假设被"参数化"

LLM 的输出经解析、归一化、裁剪后,`yaml.dump` 落盘到 `exp_plan.yaml`(`:556-559`)。真实结构(根键 `experiment_plan`)如下,注意每一块都能回溯到假设里的某个诉求:

```yaml
experiment_plan:
  topic: "...";  generated: "2026-04-25T..."
  objectives:        # 把假设的"可测预测"翻成可执行目标(primary + diagnostic)
  datasets:          # 含 factorial_design——本例 2 复杂度 × 2 参数范围 = 4 个评测条件
                     # 还含生成规模(2000 训练 / 400 验证 / 400 测试)和参数分布
  baselines:         # [{name, implementation_spec{class_name, algorithm_steps,
                     #    key_hyperparameters}, training{method, epochs, lr, batch_size}}]
                     # 本例:bpe_subword_sft_qwen2(对照 H1 的 BPE 基线)、deepcad_scratch
  proposed_methods:  # 同结构。本例:primitive_token_vocab_sft(H1 的主角)、
                     #              primitive_token_dpo(H2 的 DPO 对齐)
  ablations:         # [{name, variable, conditions:[label...], held_constant,
                     #    expected_outcome, compute_estimate}]
                     # 本例 tokenization_granularity 消融直接服务于 H1:
                     #   bpe_default / integer_only_tokens / decimal_aware_tokens
  metrics:
    primary: [{name: sequence_validity_rate,   # 就是 H1 要测的"有效率"
               formula: "(# valid) / (# total)",
               range: "[0,1]; higher is better",
               aggregation: "mean ± std over 3 random seeds"}]   # ← 3 个种子在此约定
    secondary: [operation_type_accuracy, mean_parameter_l1_error, ...]
    statistical_testing: {method: "paired bootstrap 10000",
                          correction: "Bonferroni for 3 comparisons",
                          significance: "p < 0.05"}
  compute_budget: ["1× RTX 3090 24GB", "Total 1500s", "Per-condition ~175s"]
  hypotheses_tested: ["H1: 原语 token 提升有效率;效应量区分推理 vs 检索", "H2: ..."]
```

`hypotheses_tested` 字段是显式的回链——方案明确声明自己在检验哪几条假设。本例最终是 **2 baseline + 2 proposed + 4 消融 = 8 个条件**,每条件跑 **3 个种子**。注意 `metrics.primary` 里的 `sequence_validity_rate` 正是 H1 要测的有效率,`ablations` 里的 `tokenization_granularity`(bpe_default vs decimal_aware_tokens)正是 H1 要做的对比——**假设的每个诉求都在 YAML 里找到了对应的可执行结构**。

### 1.6 条件数裁剪:防止 LLM 设计出注定超时的实验(BUG-R41-09)

写盘前还有一道重要守卫(`:458-503`)。LLM 经常会"贪心"地设计出 30 多个条件,在有限时间预算下必然全部超时、白烧算力。所以这里按时间预算设上限:

```python
_max_conditions = 8                  # 预算 ≤ 3600s
if _time_budget > 3600: _max_conditions = 12
if _time_budget > 7200: _max_conditions = 20
```

超限时的裁剪策略很讲究(`:480-503`):**优先保住 proposed_methods**(论文的主角,最多保 `_max_conditions-4` 个),剩余预算再一分为二给 baselines 和 ablations。换句话说,当方案太大时,系统宁可砍掉一些基线和消融,也要保证"被提出的新方法"能跑完——因为新方法才是论文核心,基线和消融可以少做但新方法不能缺席。

### 1.7 健壮性:归一化 + 四级 YAML 兜底

LLM 输出 YAML 这件事本身就不可靠,所以 Stage 9 有层层防护:

**字段归一化** `_normalize_plan_field()`(`:33-60`):LLM 可能把 `baselines` 写成字符串列表、字典列表、甚至一个大字典(`{"baseline_1": {...}}`)。这个函数把所有形态统一成 `list[dict]`,且当来源是字典时**保留完整结构**——把 `{"baseline_1": {...}}` 转成 `{"name": "baseline_1", ...}`,既不丢键也不丢值。

**四级解析兜底**(`:222-344`),逐级降级,任一级成功即止:
1. `_extract_yaml_block` 抽 ```yaml``` 围栏后 `yaml.safe_load`;
2. 失败则把**整段响应**当 YAML 解析(推理模型常不加围栏);
3. 还失败就**逐行扫描**,从遇到已知键(`baselines:`/`metrics:` 等)的那行开始捕获,跳过空行/注释/markdown,再尝试解析(`:234-258`);
4. 仍失败则**用更严格的"只准输出 YAML、不要任何散文"的短 prompt 重试一次**(BUG-12,`:270-292`)。

如果连重试都失败,还有两层"无 LLM 也能产出方案"的最终兜底:从 `hypotheses.md` 用正则抽方法名/基线名拼出一个最小方案(`:294-324`),或者直接用 topic 派生占位符(`:326-344`)。**无论走到哪一级,最终的 `plan` 字典都保证含那 8 个必需键**——这是契约的硬保证,下游永远能拿到完整结构,绝不会因为 LLM 抽风而拿到半截数据。

> **本跳的本质**:把一句自然语言假设,翻译成一组结构化、有算力约束、带统计检验方案的实验参数;且这些参数逐项对应假设里的"可测预测"和"证伪条件"。即便 LLM 完全失灵,契约也保证下游拿到一份结构完整的方案。

## 2. 第②跳 Stage 9 → 10:从 YAML 方案到可运行代码

这一跳把"该做什么实验"(声明式的 YAML)变成"怎么把实验跑起来"(命令式的 Python 工程)。

### 2.1 Stage 10 读入什么、把什么注入 prompt

```python
exp_plan = _read_prior_artifact(run_dir, "exp_plan.yaml") or ""  # :243
metric   = config.experiment.metric_key                         # :244  如 "validity_rate"
max_repair = 5                                                  # :245  代码修复循环次数上限
```

随后它构造一个**硬件感知、网络策略感知**的 prompt 上下文。这一段(`:252-346`)比简版写的丰富得多:

- **`pkg_hint`(可用包提示)按 GPU 分层生成**(`:273-296`):读 `hardware_profile.json`,若是高性能 GPU(tier=high),提示"可放心用 PyTorch GPU 加速";若是低显存 GPU 或 MPS(tier=limited),则提示**设计轻量实验**——模型 <1M 参数、epoch ≤20、数据集 ≤10K 样本、避免大 batch。这是把"硬件现实"翻译成对生成代码的约束,防止 LLM 写出一个在当前机器上跑不动的实验。docker 模式还会列出预装包清单,并根据网络策略(none/setup_only/full)告知"能不能 pip install"。
- **`compute_budget`(算力预算)**(`:300-312`):注入总时间上限,并要求生成代码**实现时间守卫——到预算 80% 时优雅停止**。
- **`extra_guidance`(数据集/网络指引)**(`:314-346`):按网络策略注入不同指引。network=none 时注入"严格离线"指引(不许联网下数据),full 时注入数据集下载指引,docker+setup_only 时还注入 setup 脚本指引。

最后 prompt 模板(`prompts.default.yaml:72-93`)把 `{exp_plan}` 整份 YAML、`{metric}` 主指标键、`{pkg_hint}` 都注入,并规定**输出格式契约**——这是后续 Stage 12 能解析结果的根本约定:
- 入口必须是 `main.py`,运行实验并打印指标;
- **"main.py 必须按 `name: value` 每行打印指标"**——Stage 12 的 `parse_metrics` 就是靠这个约定从 stdout 提数;
- main.py 还要写一份 `results.json` 结构化结果。

### 2.2 Stage 10 写出的多文件工程

契约要求 `output_files=("experiment/", "experiment_spec.md")`。本例 `stage-10/experiment/` 是个 7 文件的工程:`main.py`(7000+ 行,实验入口)、`cad_data.py`(数据生成 + 几何有效性 oracle)、`cad_tokenizers.py`(各种 tokenization 策略——正是 H1 要对比的东西)、`llm_models.py`(用 peft/TRL 做 LLM 训练)、`deepcad_model.py`(从头训练的 transformer 基线)、`dpo_trainer_module.py`(DPO 训练)、`requirements.txt`。

`main.py` 顶部的 docstring 和常量直接把 `exp_plan` 的结构编译成了执行计划:

```python
# 5 个训练条件(来自 exp_plan 的 baselines+proposed):
#   deepcad_scratch / bpe_sft / primitive_sft / integer_sft / dpo
NUM_MAIN_CONDITIONS = 5
NUM_SEEDS = 3                       # ← 来自 exp_plan metrics.aggregation "over 3 seeds"
PER_SEED_BUDGET = (TIME_GUARD - OVERHEAD) / (NUM_MAIN_CONDITIONS * NUM_SEEDS)  # 算力预算→每种子配额
# 指标打印契约(将被 Stage 12 解析):
print(f'condition={name} validity_rate={mean:.6f}')
```

可以清楚看到数据形态的传递:**exp_plan 的 `baselines+proposed` 数量 → 代码里的 `NUM_MAIN_CONDITIONS=5`;`metrics.aggregation` 的"3 seeds" → `NUM_SEEDS=3`;`compute_budget` → `TIME_GUARD` 常量和每种子时间配额;`metrics.primary.name` → 打印语句里的 `validity_rate`**。

副产物 `experiment_spec.md` 是给人/给下游看的规格摘要,记录入口、文件清单、主指标键、`Topic-Experiment Alignment: ALIGNED`(主题对齐自检)、约束(时间预算、自包含无网络)、以及 `Validated: N warning(s)`(代码校验结果)。

> 至于"代码具体是怎么生成出来的"——三层路由(Beast Mode/CodeAgent/Legacy)、蓝图规划、`max_repair=5` 的执行-修复循环、AST 安全校验黑名单——属于"怎么生成"的纵深机制,详见 `架构研究.md §8.2 / §8.6`。本文只关心数据交接:**exp_plan 的 conditions/metrics/budget,变成了生成代码里的循环结构、指标打印语句、时间预算常量**。

## 3. 第③跳 Stage 9 → 11:从 YAML 方案到任务依赖图

注意这一跳的起点同样是 `exp_plan.yaml`,而不是 Stage 10 的代码——**Stage 10 和 Stage 11 是同一份方案的两个平行消费者**。

### 3.1 Stage 11 怎么读、产出什么

```python

sp = _pm.for_stage("resource_planning", exp_plan=exp_plan)        # :58  json_mode=True

```

prompt 模板(`prompts.default.yaml:315-321`)用 `json_mode=True` 强制 JSON 输出,并规定 schema:`{tasks:[{id, name, depends_on, gpu_count, estimated_minutes, priority}], total_gpu_budget, generated}`。

### 3.2 `schedule.json`:把方案展开成带依赖的 DAG

LLM 读 exp_plan,把里面的条件展开成一张**任务依赖图**。本例 22 个任务,依赖结构直接反映了实验的因果次序:

```
T01 data_generation (0 GPU) ──→ T02 oracle_unit_tests
T03/T04/T05 训练 baseline+proposed(都依赖 T02,各占 1 GPU)
T05 ──→ T06 construct_dpo_pairs ──→ T07 train_dpo   ← DPO 必须在 SFT 检查点之后
T08 eval_all(依赖 T03,T04,T05,T07——评测要等所有模型训完)
T09..T20 各消融(分别依赖各自的父训练任务,复用已训好的检查点)
T21 statistical_testing(依赖所有消融——统计检验要聚合全部结果)
T22 results_aggregation(依赖 T21)
```

依赖关系不是凭空来的,而是从 exp_plan 的语义推出来的:DPO 方法本来就建立在 SFT 检查点之上,所以 T07 依赖 T06 依赖 T05;评测必须等模型训完,所以 T08 依赖所有训练任务;统计检验要对比所有条件,所以 T21 依赖所有消融。`estimated_minutes` 和 `gpu_count` 则由 exp_plan 的 `compute_budget` 推断。

> **设计观察:为什么 10 和 11 都读 exp_plan、而不是 11 读 10 的产物?** 因为"怎么实现实验"(Stage 10 的代码)和"怎么调度实验"(Stage 11 的 DAG)是**两个正交的关注点**——前者关心算法和数据,后者关心资源和顺序。让它们各自独立地从同一份方案派生,意味着二者可以并行理解、独立重跑,互不耦合。schedule.json 的 DAG 主要在多机/多 GPU 调度场景下发挥价值;在单机顺序执行时,Stage 12 实际是把整个 main.py 当一个任务跑(见下),DAG 更多是"意图记录"。

## 4. 第④跳 Stage 10/11 → 12:从代码到结构化指标

这是全流水线信息形态变化最剧烈的一跳:**人类可读但机器难解析的 stdout 文本,坍缩成机器可读的分层数字字典**。整条流水线前面所有的语义工作,到这里第一次接触"真实世界的数字"。

### 4.1 Stage 12 读入什么


### 4.2 沙箱分派与隔离执行

按 `config.experiment.mode` 经 `create_sandbox()`(`factory.py:18-108`)选后端(sandbox/docker/ssh/colab/agentic,详见 `架构研究.md §11`)。多文件工程走 `run_project(dir)`,单文件走 `run(code)`。执行前沙箱会做三件事(`sandbox.py:314-451`):把工程复制到隔离目录 `runs/sandbox/_project_1/`、**注入一份不可变的 `experiment_harness.py`**(防止生成代码篡改度量逻辑)、做符号链接逃逸检查;然后以 `PYTHONUNBUFFERED=1` 跑子进程,确保所有 stdout 都被实时捕获(否则缓冲可能丢失末尾输出)。

### 4.3 `parse_metrics()`:这一跳的灵魂(`sandbox.py:89-198`)

生成代码跑完后,它的 stdout 是一堆形如 `condition=dpo seed=0 l1_error: 21.8` 的文本行。`parse_metrics` 用**五个分支按优先级逐行匹配**,把文本坍缩成 `dict[str, float]`,键用 `/` 分层。优先级从高到低:

1. **SUMMARY 行(最可靠)**:`SUMMARY condition=X metric=Y mean=M std=S`。一行一指标,显式标注均值和标准差。产出四个键:`X/Y`、`X/Y_mean`、`X/Y_std`、以及纯 `Y`(全局兜底)。
2. **条件+比值**:`condition=X regime=fast seed=0 validity_rate: 9/10`。把 `9/10` 算成 0.9,并用 `condition + 额外 tag` 拼出复合键 `X/fast/validity_rate`,同时写 `X/validity_rate` 和纯 `validity_rate`。
3. **条件+单指标**:`condition=X [tags] metric: value`。同样拼复合键。
4. **条件+多指标(一行多个)**:`condition=dpo seed=0 l1_error: 21.8 param_csr: 0.88`。用 `finditer` 抽出该行所有 `metric: value` 对;若行内有 `seed=`,则额外写一个**逐种子键** `dpo/0/l1_error`,再写 `dpo/l1_error` 和纯 `l1_error`。
5. **纯指标行**:`l1_error_mean: 4.9`。最朴素的兜底。

两个贯穿所有分支的守卫:
- **`is_metric_name()` 名字过滤**:不是所有 `xxx: 数字` 都算指标,得通过名字检查,过滤掉日志噪声行。
- **NaN/Inf 拒绝(R5-3)**:每次 `float()` 后都查 `if math.isnan(val) or math.isinf(val): continue`——发散/崩溃产生的非有限值绝不进入指标字典,否则会污染下游的"最优值"判断。

**为什么要"键爆炸"——同一个数字写好几个键?** 因为下游(Stage 13/14)取指标时,有时知道精确的 `condition/metric`,有时只有一个模糊的 `metric_key`。同时写 `condition/metric`、`condition/metric_mean`、逐种子 `condition/seed/metric`、和纯 `metric` 兜底键,意味着下游无论用精确键还是模糊匹配都能取到值。**代价**是:纯兜底键(如 `l1_error`)会被后写的行覆盖,所以全局兜底键只反映 stdout 里最后一行的值——下游若要可靠取值,应该用分层键而非兜底键(Stage 13 的 `_find_metric` 正是这么做的,见 §5)。

我实测验证了这个行为:对 `"SUMMARY condition=dpo metric=l1 mean=2.5 std=0.1\ncondition=bpe seed=0 acc: 0.9"`,`parse_metrics` 产出 `{'dpo/l1', 'dpo/l1_mean', 'dpo/l1_std', 'l1', 'bpe/0/acc', 'bpe/acc', 'acc'}`——与上述规则完全一致。

### 4.4 `SandboxResult` 落盘与三态状态判定

执行结果先封装成 `SandboxResult{returncode, stdout, stderr, elapsed_sec, metrics, timed_out}`(`:281-300`),然后判定运行状态并写 `runs/run-1.json`(`:367-389`):

```json
{"run_id":"run-1", "task_id":"sandbox-main", "status":"completed",
 "metrics":{...分层指标字典...}, "elapsed_sec":1234.5,
 "stdout":"...", "stderr":"", "timed_out":false, "completed_at":"..."}
```

**run_status 三态判定(R6-2 守卫,`:334-358`)**——这是个比"看退出码"聪明得多的判定:
- `completed` = 退出码 0 **且** 未超时 **且** stdout 里没有失败信号;
- `partial` = 超时了**但已经采到指标**——数据虽不完整但可用,不浪费已烧的算力;
- `failed` = 其余情况。**关键:即便退出码是 0,只要 stdout 里出现 `FAIL:` / `NaN/divergence` / `Traceback (most recent` 这些失败信号,也判为 failed**。这道守卫防的是"假成功"——生成代码可能 catch 了异常、打印了 traceback 却仍以 0 退出,naive 的判定会误以为实验成功。

两个补充产物:若沙箱自己没产出 `results.json`,会从解析到的指标自动生成一份 `{"source":"stdout_parsed","metrics":{...}}`(`:383-385`);若超时,还会写 `time_budget_warning.json`(R11-6),记录已完成的条件和种子数,供人判断要不要加预算重跑。

## 5. 终点之后:Stage 13/14 如何消费 `runs/`

数据到了 `runs/` 还没完——它要被反过来用来检验假设。
