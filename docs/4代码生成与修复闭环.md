# AutoResearchClaw 代码生成与修复闭环深度解析

> **为什么写这份文档**:把"一份 YAML 实验方案"变成"一份能真正跑出科学结果的多文件 Python 工程",是整条流水线里**工程难度最高、最容易失败**的一环——LLM 写的代码会有语法错、跑崩、假装跑通(打印硬编码指标)、或者跑通了但实验设计是退化的(两个消融条件输出完全一样)。AutoResearchClaw 为此构筑了一套相当复杂的**多层生成 + 多重校验 + 双闭环修复**机制。本文把这套机制完整拆开,逐层讲清**每个组件做什么、数据怎么在组件间流动、为什么这么设计、各种失败如何兜底**,而不是罗列要点。所有结论有 `file:line` 证据。
>
> 与 `架构研究.md §8.2/§8.6`(概览)互补:那里点到为止,这里展开到可执行细节。涉及代码安全扫描的部分见 `安全模型.md`。

---

## 0. 全局认知:这里其实有"两套修复闭环"

理解这个子系统,最重要的一点是:**AutoResearchClaw 在两个不同阶段、用两套独立机制做"修复",目标完全不同**。很多人会把它们混为一谈,实际上:

| | **生成时修复**(Stage 10) | **结果时修复**(Stage 13/14 区域) |
|---|---|---|
| 代码位置 | `code_agent.py` + `_code_generation.py` | `experiment_repair.py` |
| 目标 | 让代码**能跑通**(语法对、不崩、API 用对) | 让实验**结果有意义**(指标非退化、消融有效、达到质量门槛) |
| 触发时机 | 代码生成阶段,实验还没真跑 | 实验跑完后发现结果太差/不足 |
| 判据 | `validate_code` 通过 + 沙箱 returncode==0 | `assess_experiment_quality` 判定 `sufficient` |
| 修复手段 | 校验反馈 / 执行报错 / 评审意见喂回 LLM | 诊断报告(`diagnose_experiment`)喂回 LLM |

**一句话**:生成时闭环管"代码跑不跑得起来",结果时闭环管"跑出来的东西像不像真实验"。下面先讲生成时(§1-3),再讲结果时(§4),最后讲它们如何衔接(§5)。

## 1. Stage 10 的三层路由:Beast Mode → CodeAgent → Legacy → 兜底

`_execute_code_generation`(`_code_generation.py:227`)读入 `exp_plan.yaml` 和 `metric_key` 后,按一条**带降级的路由链**决定由谁来写代码(`:489-804`)。这条链的设计哲学是"能力强的优先,失败就降级到更稳的",共四级:

### 1.1 第一层:Beast Mode(OpenCode 外部 agent,可选)

只有当 `config.experiment.opencode.enabled` 为真时才考虑这一层(`:496`)。它先用 `score_complexity()`(`:505-509`)给本次任务打一个**复杂度分**——输入是实验方案、主题、以及**本 run 此前的历史失败次数**——若分数超过 `complexity_threshold`(默认 3.5),`score_complexity` 就给出 `recommendation == "beast_mode"`(`:528`)。

复杂度够高之后还有一道**人工闸门**(`:529-547`):如果 `opencode.auto` 为 False,系统会通过 HITL adapter 问人"复杂度=X,要不要路由到 OpenCode?";没有 HITL adapter 又没开 `auto`,就跳过 Beast Mode。这道闸门的意义在于:OpenCode 是个会自主多轮操作的外部 agent,成本和不确定性都高,所以默认要人点头。

真正 engage 后(`:551-599`),`OpenCodeBridge.generate()` 去跑外部 agent,结果落盘 `beast_mode_log.json`(记成功与否、耗时、文件清单、错误、模型)。**成功**(`_oc_result.success and files`)就设 `_beast_mode_used=True` 并把后续两层全跳过;**失败**就记一条 warning,**优雅降级到 CodeAgent**(`:603-607`)。这个"成功即短路、失败即降级"的模式,是整条路由链的统一节奏。

> 定位:Beast Mode 是给"多文件、自定义算法、本 run 反复失败"这类高复杂度任务准备的重武器,默认不开,开了也要复杂度够高 + 人审。

### 1.2 第二层:CodeAgent(高级 LLM 代码 agent)

如果没走 Beast Mode 且 `config.experiment.code_agent.enabled` 且有 LLM(`:615`),就进 CodeAgent——这是**默认的主力路径**,也是本文 §2 的主角。它会先做领域探测,对**非 ML 领域**还会跑一个 `CodeSearchAgent` 去搜真实 API 用法和参考仓库(`:653-669`),把这些作为额外上下文喂给 agent(ML 领域因为 LLM 内置知识够用而跳过)。然后构造 `CodeAgent`(`:673-682`)并调 `generate()`,产物落盘 `code_agent_log.json`(记 LLM 调用数、沙箱运行数、最佳得分、树搜索探索节点数、评审轮数)和 `architecture_spec.yaml`。

### 1.3 第三层:Legacy 单发生成 + 校验循环

如果 CodeAgent 没开但有 LLM(`:718`),走传统单发路径:一次 `_chat_with_prompt` 拿到响应,`_extract_multi_file_blocks` 抽多文件;**空响应会用更高 token(32768)重试一次**(`:750-766`,因为推理模型常把 token 耗在思维链上)。然后进入一个 `max_repair=5` 的校验-修复循环(详见 §3)。

### 1.4 最终兜底:硬编码的 numpy 合成实验

如果以上都没产出文件(`:776`),系统不会让流水线断掉,而是塞进一段**硬编码的 numpy 参数扫描实验**(`:777-804`)——3 个条件 × 3 个种子,在一个合成目标上跑,并按指标打印契约 `print(f'condition={cond} {metric}: {val}')` 输出。这保证了即便 LLM 完全失灵,Stage 12 也有东西可跑、有指标可解析。这是"优雅降级"哲学的极致体现:宁可跑一个无意义的占位实验,也不让整条流水线崩在这里。

## 2. CodeAgent 的五相流水线(主力路径详解)

`CodeAgent.generate()`(`code_agent.py:192-279`)按一条五相流水线工作,每一相都可由 `CodeAgentConfig`(`:42-79`)开关。下面逐相展开。

### 2.1 Phase 1 — 蓝图规划(`_phase1_blueprint`,`:283-326`)

不直接写代码,而是先让 LLM 产出一份**实现蓝图**:用 `architecture_planning` 子 prompt,要求输出一份 YAML,列出要建哪些文件、每个文件的职责、文件间依赖、以及 `generation_order`(生成顺序)。非 ML 域还会把 `_build_domain_context`(领域指引 + 代码搜索结果)拼到蓝图 prompt 后面(`:300-306`)。响应里抽出 ```yaml``` 块,`_parse_blueprint` 解析成结构化 dict。

**为什么先规划再写?** 因为架构错误(文件切分不合理、依赖搞反)如果等到写完代码才暴露,返工成本极高;先出蓝图,等于把架构决策提前到最便宜的阶段。蓝图解析失败(`_is_valid_blueprint` 不过)会导致后面降级到单发生成——蓝图是顺序生成的前提。

### 2.2 Phase 2 — 顺序生成 + CodeMem(`_phase2_sequential_generate`,`:472-576`)

这是 CodeAgent 最精巧的部分。它**按蓝图的 `generation_order` 逐个文件生成**(`:496` 排序),而不是一次性让 LLM 吐出所有文件。每生成一个文件,就用 `_build_code_summary`(`:608-653`)对它做一次 **AST 分析,提取出类/方法签名/函数/导入的压缩摘要(CodeMem)**。

关键在于**依赖上下文怎么传**(`:508-545`):生成文件 N 时,对它在蓝图里声明的每个依赖,系统会把依赖文件的 **CodeMem 摘要**(`dep_summaries`)和**完整代码**(`dep_code`)都拼进 prompt。这样后生成的文件就"知道"前面文件里有哪些类、方法签名长什么样,从而正确地 import 和调用,而不是凭空捏造一个不存在的接口——这是跨文件 `NameError`/`AttributeError` 的主要来源。`exp_plan` 在这里被截断到 4000 字符(`:543`)以防 token 溢出。最后还有一道保险:如果没生成出 `main.py`,就把第一个文件提升为 `main.py`(`:566-571`)。

> **设计精髓**:用 AST 摘要(而非全量代码)做跨文件上下文,在"让后续文件了解前文接口"和"不爆 token"之间取得平衡。这是把"几千行多文件工程"拆成"可控的逐文件生成"的核心技巧。

### 2.3 Phase 2.5 — 硬校验门(`_hard_validate_and_repair`,`:657-705`,E-03)

文件齐了之后,跑一轮 **AST 静态硬校验**,且这一轮的精髓是**把问题分成 CRITICAL 和 WARNING 两档**(`_hard_validate`,`:707-799`),只有 CRITICAL 才触发返工(最多 `hard_validation_max_repairs=4` 次),WARNING 只记日志。哪些算 CRITICAL,体现了这个项目踩过的坑:

- **语法错**(总是 critical);
- **类质量问题**里的特定几种:`identical AST to parent`(子类和父类 AST 完全相同——假继承)、`NOT a real ablation`(消融类没有真实差异)、`empty or trivial subclass`(空壳子类)、在 `forward()` 里创建 `nn.Module`(每次前向都新建模块,训练必然出问题)——这些都升级为 critical;
- **硬编码指标**(`hardcoded metric`)和 `trivial computation`——critical,因为这是"假装跑出结果"的典型;
- **API 正确性**里会导致 `NameError`/`Import-usage mismatch`/`does not exist` 的——critical;
- **变量作用域**里会导致 `UnboundLocalError` 的——critical;
- **跨文件 import 一致性**:检查本地 import 是否能解析到实际生成的模块(`:789-799`)。

CRITICAL 命中后由 `_repair_critical_issues`(`:872`)做**针对性返工**——只把具体的 critical 列表喂给 LLM 要求修。

> **为什么分级?** 因为如果把所有 lint 级别的小毛病都当硬错误返工,会陷入"修了 A 又冒出 B"的震荡,还会让 LLM 过度修改(比如删掉运行时需要的 import)。只对"真正会让实验失效或造假"的问题返工,是工程上的务实取舍。注意这里检的"假消融/硬编码指标"已经超出"代码能不能跑",开始触及"实验是不是真的"——是生成时闭环对结果质量的前置防御。

### 2.4 执行-修复循环(`_exec_fix_loop`,`:962-979`)

校验过了不代表能跑。如果有沙箱(`sandbox`/`docker` 模式才有),就**实际把代码跑起来**,最多 `exec_fix_max_iterations=3` 轮:returncode==0 就 break;崩了就调 `_fix_runtime_error`。

`_fix_runtime_error`(`:1029-1072`)有两级策略:**优先针对性修复(E-05)**——`_parse_error_location` 解析 Python traceback 找出出错的文件名和行号,只把那个文件 + 聚焦的上下文窗口发给 LLM 修(`_targeted_file_repair`);解析不出位置才**降级到全文件修复**,把所有文件上下文 + stderr 尾部(3000 字符)+ stdout 尾部(50 行)发给 LLM。

另外,生成代码时(`_generate_code`,`:1000-1009`)会**强制注入数值稳定性要求(BUG-004)**:梯度裁剪 `clip_grad_norm_(params, 1.0)`、每步检查 NaN loss(`if torch.isnan(loss): print('FAIL: NaN detected'); break`)、指标记录时 guard NaN/Inf、RL 场景裁剪 reward。注意那句 `print('FAIL: ...')` 正是 Stage 12 的 R6-2 假成功检测要抓的失败信号(见 `端到端追踪.md §4.4`)——**生成时主动埋下失败信号,好让执行时能识别"假成功"**,两个阶段在这里有精巧的呼应。

### 2.5 Phase 3 — 树搜索(`_phase3_tree_search`,`:1196-1278`,默认关)

`tree_search_enabled` 默认 False,因为它很贵。开了之后:先生成 `tree_search_candidates=3` 个候选实现,在沙箱里各自评估打分(`_score_node`,`:1298-1312`:能跑 +1.0、有 >100 字符输出 +0.3、有指标 +0.5、指标里含目标 metric_key 再 +0.5、stderr 含 Error -0.2),按分排序;若最佳候选还跑不通,就对**排名前二的崩溃候选**生成修复变体(branch),最多 `tree_search_max_depth=2` 层。本质是"多路并行探索 + 沙箱择优",用算力换成功率,适合解空间宽、单发难一次中的的难任务。

### 2.6 Phase 4/5 — coder-reviewer 评审对话(`_phase4_review`,`:1316-1377`)

最后默认跑 `review_max_rounds=2` 轮评审:用 `code_reviewer` 子 prompt 让一个"评审 agent"看代码,返回 JSON `{verdict, score, critical_issues}`;若 verdict 是 APPROVE 或没有 critical issue 就结束;否则把 critical 列表 + 当前代码用 `code_generation` 的系统 prompt 发回去让"coder"修,要求输出所有文件(含未改的)。这是一个轻量的"自我审查"环,在交付前再过一道独立视角。

## 3. Legacy 单发路径的校验循环(`_code_generation.py:806-...`)

不走 CodeAgent 时,Legacy 路径用一个更朴素的循环兜底质量:对每个 `.py` 文件跑 `validate_code`,不过就进 `max_repair=5` 的修复循环(`:809-839`)。这里有个**容易忽略但很重要的细节**(`:818-822`):**只把 severity==error 的问题喂回 LLM,warning 不喂**。注释说明了原因——警告不阻断校验,把它们也发给 LLM 会诱导过度修改(比如把运行时才用到的 import 当成"未使用"删掉)。这与 CodeAgent 的 critical/warning 分级是同一种工程智慧:**只对真正阻断性的问题做返工**。

`max_repair` 从 3 提到 5(BUG-14 注释,`:245`),是因为有些关键 bug 需要更多轮才能修好。

## 4. 结果时修复闭环(`experiment_repair.py`)

这是**完全独立的第二套闭环**,发生在实验跑完、发现结果不行之后。入口 `run_repair_loop`(`:274`)。

它先用 `assess_experiment_quality` 评估当前结果;如果已经够好(`sufficient`)就直接返回。否则进入 `max_cycles`(受 `MAX_REPAIR_CYCLES` 硬上限约束)的循环(`:353-472`),每一轮做五件事:

1. **诊断**:`diagnose_experiment`(`:358`)综合实验摘要、方案、refinement log、stdout/stderr、以及**此前所有轮的诊断历史**(`prior_diagnoses`),产出一份结构化诊断——这一轮到底哪里出了问题。把诊断历史累积传入,是为了让后续轮"知道前面试过什么、别重复犯错"。
2. **建修复 prompt**:`build_repair_prompt`(`:369`)把诊断 + 当前代码 + 方案 + 时间预算组装成修复指令。
3. **拿修复代码**:`_get_repaired_code`(`:375`)——LLM 为主,OpenCode 为备。
4. **版本化保存 + 重跑**:修好的代码存到 `stage-14_repair_v{cycle}/experiment/`(`:390-396`,每轮独立目录,不覆盖),在沙箱里重新跑(`:403`)。
5. **重评 + 追踪最优**:从重跑结果构建新摘要,`assess_experiment_quality` 重评,`_summary_quality_score` 打分;**只有新分高于当前最优才更新 best**(`:444-447`)。若新结果达到 `sufficient`,立即成功返回(`:459-469`)。

循环耗尽后(`:477-494`),**只有当某一轮真的改进了结果**(`best_updated`)才把最优摘要 promote 成 `experiment_summary_best.json`(`:485-487`)——这与 `runner.py` 的 `_promote_best_stage14` 配合,确保论文阶段用到的是历轮最优而非最后一轮(见 `架构研究.md §4.3`)。`select_best_results`(`:196-232`)则在所有轮里按主指标/条件数选最优摘要。

> **设计要点**:结果时修复用"诊断驱动"而非"报错驱动"——因为这时代码能跑、没崩,问题出在"结果退化/不足"这种语义层面,只有靠 `diagnose_experiment` 的结构化分析才能定位。版本化每一轮 + 只在改进时 promote,是防止"越修越差"的关键守卫。

## 5. 两套闭环如何衔接(全局流程图)

```
Stage 10 代码生成(生成时闭环:让代码能跑)
  ├ Beast Mode? ──成功→ 用 OpenCode 产物
  │              └失败→↓
  ├ CodeAgent(默认主力):
  │    Phase1 蓝图 → Phase2 顺序生成+CodeMem → Phase2.5 硬校验(critical/warning)
  │    → 执行-修复(targeted/full,注入数值稳定性) → [Phase3 树搜索·默认关] → Phase4 评审
  │              └ CodeAgent 没开→↓
  ├ Legacy 单发 + max_repair=5 校验循环(只喂 error)
  │              └ 全失败→↓
  └ 兜底:硬编码 numpy 合成实验
        │
        ▼  experiment/ + experiment_spec.md
  Stage 11/12 排程与执行 → runs/metrics
        │
        ▼  若结果太差/不足
  Stage 13/14 区域(结果时闭环:让结果有意义)
  experiment_repair.run_repair_loop:
    每轮 diagnose → fix(LLM/OpenCode) → 存 stage-14_repair_v{n}/ → 重跑 → 重评 → 追踪最优
    sufficient 即停;耗尽则 promote 历轮最优 → experiment_summary_best.json
```

衔接点在于:**生成时闭环尽最大努力交付一份"能跑且不假"的代码**,但它无法预知真实数据下结果会怎样;一旦真跑出来结果退化,就由**结果时闭环**接手,带着"实验已经跑过、数据长这样"的诊断信息去针对性地改代码重跑。两者一前一后,覆盖了"代码层失败"和"结果层失败"两类完全不同的问题。

## 6. 设计要点总览(为什么这么设计)

| 机制 | 出处 | 意图 |
|------|------|------|
| 三层路由 + 成功短路/失败降级 | `_code_generation.py:489-720` | 能力强者优先,失败逐级降到更稳路径,绝不让流水线断 |
| 最终 numpy 兜底实验 | `:776-804` | LLM 全失灵也有可跑、可解析指标的占位实验 |
| Beast Mode 复杂度阈值 + HITL 闸门 | `:505-547` | 重武器只在高复杂度时用,且默认要人审(成本/不确定性高) |
| 先蓝图后写码 | `code_agent.py:283-326` | 把架构错误提前到最便宜的规划阶段暴露 |
| 顺序生成 + CodeMem AST 摘要 | `:472-576` | 后续文件了解前文接口,杜绝跨文件 NameError;摘要而非全量,防 token 爆 |
| 硬校验 critical/warning 分级 | `:707-799` | 只对"会让实验失效/造假"的问题返工,避免修复震荡和过度修改 |
| 假消融/硬编码指标判 critical | `:738-763` | 生成时就拦截"假装跑出结果"的代码 |
| 针对性修复优先(E-05) | `:1029-1072` | 解析 traceback 只改出错文件,比全文件修复更精准省钱 |
| 注入数值稳定性 + FAIL 信号 | `:1000-1009` | 主动埋失败信号,呼应 Stage 12 的假成功检测 |
| 树搜索默认关 | config 默认 | 多路探索很贵,只在难任务显式开启 |
| 只喂 error 不喂 warning | `:818-822` | 防 LLM 过度修改(删掉运行时需要的 import) |
| 结果时修复:诊断驱动 + 诊断历史累积 | `experiment_repair.py:358-366` | 结果退化是语义问题,需结构化诊断;历史防重复犯错 |
| 版本化每轮 + 只在改进时 promote | `:390-396, 444-487` | 防"越修越差",保证论文用历轮最优 |

## 7. 关键配置项(`CodeAgentConfig`,`code_agent.py:42-79`)

| 配置 | 默认 | 含义 |
|------|------|------|
| `architecture_planning` | True | 是否做 Phase 1 蓝图 |
