# Stage 10 → 12 Smoke Test

> Introduced in commits: `d025162` (harness + config + prompt), `e435297` (supporting observability).
> Positioning: **Fix for a pipeline design flaw** — Previously, there was no runtime validation gate between code generation (Stage 10) and full execution (Stage 12).

---

## 1. What bug does this address?

During round 4 (run-4), the pipeline was repeatedly stuck due to **random runtime logic bugs** generated by Beast mode: every time Stage 10 was rerun, the generated `main.py` was syntactically valid and passed the validator's AST/import static checks, but crashed during the full execution in Stage 12. Instances encountered:

| # | Bug | Crash Point | Symptom |
|---|-----|--------|------|
| 1 | Double conversion `deepcad_json_to_cadquery(extract_text_from_sample(...))` | Data Preparation | GT calibration=0, all conditions 0 |
| 2 | `from deepcad_transpiler import get_operation_count` (name does not exist) | Startup Import | `ImportError`, immediate crash |
| 3 | `dataset_split=None` overwriting input in `prepare_sft_texts` | Data Preparation | `len(None)` crashes every condition |
| 4 | `device_map={'':0}` without restricting `CUDA_VISIBLE_DEVICES` → HF Trainer auto DataParallel | `trainer.train()` first step | `chunk expects ≥1-dim tensor` |

**Common Characteristics**: ① Undetectable by the validator (these are runtime logic/config errors, invisible to static syntax/import checks); ② **All crashed within the first few minutes of startup, data preparation, or the first step.** None crashed deep into training.

**Core Pain Point**: These are random noise. Writing prompt rules for each is playing whack-a-mole. What is truly missing is a **runtime validation gate post-generation but pre-full execution.** Discovering a crash only after hours of full execution is extremely costly (this cost days during run-4).

---

## 2. The Approach

**Insert a smoke test between Stage 10 (Code Gen/Validation) and Stage 12 (Full Execution):** Run the generated project with an extremely small budget to catch the aforementioned runtime crashes within minutes. Feed the traceback back into the repair loop. If it cannot be fixed, block the stage.

This leverages the characteristic that "target bugs crash in the first few minutes": **Even if the generated code does not scale down, running it under a tight timeout without crashing = startup bugs excluded.** Combined with the `ARC_SMOKE` hook, it can complete a full run of all conditions in 1–2 minutes.

### Three-State Determination
`_run_smoke_test()` runs `main.py` with `ARC_SMOKE=1` and a time limit, returning:
- **pass**: ① Clean exit (returncode 0); **OR** ② Maxes out the timeout window without crashing (startup bugs excluded, deemed passed).
- **fail**: Non-zero exit → Append tail of `stderr` (traceback) and hand it to the repair loop.
- **skip**: The smoke test harness itself errors out (e.g., sandbox creation failure) → Does not block the stage (issues an alert only).

### Repair Loop (Reusing rigor-repair pattern)
Fail → Feed traceback back to LLM (requesting root cause fix) → `_extract_multi_file_blocks(assume_main=False)` to extract + **merge** into files + rewrite `experiment/` → Rerun smoke test. Max **2 times**. If it still fails → write `SMOKE_FAILED.md` and return `StageResult(FAILED)`, blocking entry to Stage 12.

## 3. Changes to the Original Project

### 3.1 Configuration `researchclaw/config.py`
`ExperimentConfig` adds two fields (and YAML loader parsing):

| Field | Default | Meaning |
|------|------|------|
| `smoke_test_enabled` | `True` | Whether to enable the smoke test |
| `smoke_test_timeout_sec` | `600` | Time limit for `main.py` execution (seconds; **excludes** provisioning, which uses `provision_timeout_sec`) |

YAML override example (under `experiment:` block in `config.arc.yaml`):
```yaml
experiment:
  smoke_test_enabled: true        # Disable smoke test: false
  smoke_test_timeout_sec: 600
```

### 3.2 Harness `researchclaw/pipeline/stage_impls/_code_generation.py`
- Added `_run_smoke_test(exp_dir, config, timeout_sec) -> (status, detail)` (three-state).
- Inserted before the final `return` of Stage 10: **Gating** + Smoke Test + Repair Loop + `SMOKE_FAILED.md` blocking.
- **Gating Conditions** (All must be met to run smoke):
  `smoke_test_enabled` AND `mode ∈ {sandbox, docker}` AND `files` contains `main.py` AND **the corresponding mode's `network_policy != "none"`** (reads `docker.network_policy` or `sandbox.network_policy`; must be able to provision, otherwise missing dependencies will cause false positives).

### 3.3 Codegen Prompts `opencode_bridge.py` (beast) + `prompts/ml.py` (ml)
Added the **`ARC_SMOKE` hook** convention: Requires `main()` to check `if os.environ.get("ARC_SMOKE")` at the top and **scale all cost knobs to the minimum while still covering every condition path** (seeds=[0], train steps/epochs→1, eval/proxy/collection samples→2, RL steps→1, datasets→a few lines). This allows the smoke test to run **all** conditions in 1–2 minutes while still hitting real tools/oracles (scaling down size, not changing implementation).

### 3.4 Supporting Observability (`e435297`, enabling root-cause location on smoke fail)
- Codegen prompt requires: **Every long loop** (training/eval/proxy/rollout) must periodically update `progress.json` and print progress.
- **`except` blocks must use `traceback.print_exc()`** (note that the sandbox logs `stderr` separately to `stderr.log`)—otherwise, a smoke test fail leaves only a single-line message, making root cause location impossible.

### 3.5 Artifacts
- On failure: `stage-10/SMOKE_FAILED.md` (contains traceback, visible at the gate), stage status becomes `FAILED`.
- Smoke test's own sandbox: `stage-10/smoke_sandbox/_project_N/` (isolated venv + stdout.log/stderr.log).

## 4. Execution Notes

1. **Initial Provisioning Overhead**: The smoke test creates an isolated venv + pip installs in `smoke_sandbox` (~10 min, one-time). Stage 12 will create its own venv later (**currently not reused**, totaling ~10 extra minutes). Compared to a full multi-hour run and the cost of "crashing during full run and restarting," this is negligible. **Optimization Todo**: Let Stage 12 reuse the smoke test's venv.
2. **Dependencies Must Be Installable**: The gate requires `network_policy != none`. If set to `none` (no provisioning), the smoke test will **falsely report fail** due to missing dependencies—this is why the smoke test is intentionally bypassed in this mode.
3. **`ARC_SMOKE` is a prompt convention, reliant on LLM compliance**: If the newly generated `main.py` does not implement this hook, the smoke test will run at **full scale** → likely timing out at `smoke_test_timeout_sec` (600s) → resulting in **pass (inconclusive)**. This still catches the target "first few minutes crash," but **cannot confirm** deeper paths. **After dispatch, verify** whether the new `main.py` actually has the `ARC_SMOKE` branch (e.g., `grep ARC_SMOKE`).
4. **Timeout Semantics**: 600s is the execution limit for `main.py`, **excluding provisioning**. If a condition is extremely slow per step (e.g., un-accelerated eval), even with ARC_SMOKE scaled down to 2 samples, it might approach 600s. If frequent timeout-passes are observed, consider increasing `smoke_test_timeout_sec` or ensuring accelerations (fp16/batching/tight caps) are active.
5. **Repair Loop Limit is 2**: Two consecutive failures to fix via traceback will block the stage. Seeing `SMOKE_FAILED.md` indicates a bug too hard for the LLM to self-repair; a human must review the traceback.
6. **stderr vs stdout**: The smoke test's traceback is in `smoke_sandbox/_project_N/stderr.log`; `SMOKE_FAILED.md` extracts the tail. Inspect these directly when troubleshooting.
7. **Skip does not block**: If logs show "smoke test harness error", this is an issue with the smoke framework itself (not a bug in the generated code), and the stage proceeds normally. Be careful not to let real issues slip through as skips.
